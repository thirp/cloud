# EXAMPLE ONLY — not the vendor's playbook, not a built-in Thirp diagnostic

EXAMPLE ONLY. Vendors author their own product checks, interpretation, and remediation. Thirp supplies scoped connection primitives. This reference skill requires a vendor Organization Service Identity or the person's signed-in Thirp session; never request a customer's credentials in chat.

1. Diagnose: collect the customer reference, case ID, symptom, and named Service requirements from the vendor's own checks.
2. Provision: `list_environments`; if needed `ensure_environment` by customer/deployment external reference or name. Supply `os` and `arch` from the vendor’s knowledge of the customer host (for example, `"os":"linux","arch":"amd64"`), or ask the vendor engineer. Never sniff the browser or mail client. A stored pair is reused when both keys are omitted; install mail refuses until the Environment platform is known. Inspect Services and agent_status. `send_agent_install` emails the customer the one-use enrollment command. Wait for the customer to install/configure the customer-side Thirp Agent (`thirp-agent`) and its local targets. This Agent is separate from the vendor's AI client that calls MCP. A wrong Service map requires a new `send_agent_install` using the same Agent display_name and additional Service IDs, then another enroll. There is no ensure_services tool.
3. Approve: `request_access` for the required catalog Service IDs, reason/case ID, and shortest useful window. `send_approve_link` emails the Environment Approvers. Poll `grant_status`. A chat yes cannot approve; the Approver signs in, reviews, and explicitly posts Approve on the page. Stop if denied or expired.
4. Connect: `connect` for each active grant returns a bounded credential, Broker endpoint and TLS name. Use the CLI/SDK to open the stream. Keep credentials private. Run only the vendor's own authorized checks. Streams reset at expiry or revocation.
5. Report: `get_report` for the request and `list_audit` with Environment/action/time filters; summarize observations with the case ID and connection history. Do not put credentials in reports.
6. Cleanup: `revoke_access` for every grant when diagnosis finishes, even if a check fails. Confirm `grant_status` is revoked and close the client streams.
